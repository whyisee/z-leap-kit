## whyisee-community 移动端：服务端 + 客户端开发设计方案

- 产出 `whyisee-community/docs/mobile-app-dev-design.md`（承接 `mobile-app-design.md` 的混合壳决策，补服务端 API 层与 Flutter 客户端落地细节）。
- 实测澄清 4 处与旧文档假设不符的事实：
  1. 已有 6 个只读 JSON 端点（`src/server/api/app.ts` 的 health/categories/tags/topics/topics/:id + `/api/recommendations/see`），不是"没有 API"；缺的是详情聚合、写操作、分页游标、token 认证。
  2. Astro 6.4.2 `security.checkOrigin` 默认 true，判定逻辑在 `node_modules/astro/dist/core/app/middlewares.js`：非 GET 且 content-type 为 form 类（含 multipart）时要求 `Origin === url.origin`，否则 403。→ **原生 multipart 上传必被拒**，客户端需显式带 `Origin: https://whyisee.xyz`。
  3. `/t/[id]/[slug]` 只是 301 到 `/t/:id`，深链只需 `/t/:id`。
  4. 迁移（`scripts/migrate.ts`）是往 `migrations[]` 追加 `{version, sql}` 对象，不是独立 SQL 目录。
- 方案要点：`/api/v1` Hono 子应用做协议适配层（禁止写 SQL/业务），业务复用 `src/server/services/*`；token 直接用 `sessions.id`（不加 JWT），加 `sessions.client` 列区分 web/app，90 天 + 轮换；feed 的 `latest` 用 keyset 游标、`hot/recommend` 用 offset + 客户端去重；详情聚合批量查回帖互动（现状 `t/[id].astro:52` 是 N+1）；`last_seen_at` 加 5 分钟节流。
- 客户端：Riverpod + go_router(StatefulShellRoute.indexedStack) + dio(401 单飞刷新) + freezed + flutter_widget_from_html_core（渲染服务端 contentHtml，不在 Dart 重写 markdown）。
- 工作量估：服务端 ~5.5 人日，客户端 P0+P1 ~5 人日。
